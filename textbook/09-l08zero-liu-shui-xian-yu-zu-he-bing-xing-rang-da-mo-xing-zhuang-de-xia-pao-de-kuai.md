# L08｜ZeRO、流水线与组合并行：让大模型装得下、跑得快

本章只需要基本 Python、矩阵运算和概率/求导知识，新的术语会在使用时解释。我们先交代集群与拓扑约束，再从 DDP 的重复存储引出 ZeRO/FSDP，随后讨论流水、序列/上下文、专家并行，最后组合成训练配方。

## 1. DDP 复制了什么

先把跨卡训练需要的对象说清：参数定义模型，梯度是本步损失对参数的导数，优化器状态保存更新历史，激活是前向中间值。FP32 每元素四字节，BF16 两字节；模型状态与当前数据产生的激活是两份账。

DDP 是复制式数据并行：每卡都有完整模型，处理不同样本，再同步梯度。增加卡数首先增加吞吐，不自动减少每卡静态状态。集群链路有带宽与延迟差异，分片意味着要在需要时把别人保存的部分取来，存储收益必须连同通信成本计算。

一个混合精度 Adam 模型可能保存 BF16 参数 2N 字节、BF16 梯度 2N、FP32 主权重 4N，以及两个 FP32 状态共 8N，合计 16N，还没算激活。N=10亿时就是约 16GB 的静态数组。

如果八张卡都保存一份，就出现大量重复。ZeRO 的思想是：**只让某些状态由某张卡负责，其他卡在需要时交换相应信息。** 它没有把数学模型切成互不相干的部分，而是在优化数据所有权。

### 从数据中心约束到实际配方

比较 torus/mesh、树状交换网络及更大互联域时，重点是通信模式与拓扑匹配；不同代际会改变拓扑，不能把“TPU 总是 torus、GPU 总是树”固定下来。分析具体系统时，要同时记录硬件代际、互联域与配置版本。

### 拓扑与代际

mesh/torus、树状交换和大互联域展示的是工作负载与布线成本的取舍。all-to-all 可达不代表每对设备都有独占直连；还需考虑路径、拥塞和交换带宽。 讨论的较新 TPU 网络本身就反驳“所有 TPU 永远是同一拓扑”的概括。系统总功耗比较同时改变设备数量和系统规模，不能直接换算成完成相同训练任务的能耗差异。

## 2. 三个 stage 分别切什么

ZeRO 把重复的模型状态划分所有权。stage 1 先分优化器状态，stage 2 再分梯度，stage 3 连参数也按片保存。P 是分片组中的设备数，N 是该组需要负责的参数数；不等同于整个训练集群的所有设备。FP32 主权重若存在，也应明确归在哪一项中。

| 方案 | 参数 | 梯度 | 优化器相关状态 |
| --- | --- | --- | --- |
| DDP | 复制 | 复制 | 复制 |
| ZeRO-1 | 复制 | 可完整形成 | 分片 |
| ZeRO-2 | 复制 | 分片保存 | 分片 |
| ZeRO-3／FSDP 思路 | 分片保存、按需聚合 | 分片 | 分片 |

具体框架对主权重和缓冲的实现不同。用上面的 16N 教学账本，P 卡静态容量可以近似写成：ZeRO-1 为 `4N+12N/P`，ZeRO-2 为 `2N+14N/P`，ZeRO-3 为 `16N/P`。实际峰值还要加当前聚合的参数、通信 bucket 和激活。

因此“切了参数就一定能装下”不成立。单个不可再拆的大层、长序列激活或预取缓冲仍可能超出显存。

### 12 字节容量表不是训练可用容量

再使用 12 bytes/param 的假设：BF16 参数、梯度、两份 moment，加 FP32 主权重。8 张 80GB 卡的静态账本如下（十进制近似）：

| 策略 | 每卡 bytes/param | 仅静态容量上限 |
| --- | --- | --- |
| 复制 | 12 | 6.67B |
| ZeRO-1 | `4+8/8=5` | 16B |
| ZeRO-2 | `2+10/8=3.25` | 24.62B |
| ZeRO-3 | `12/8=1.5` | 53.33B |

这些数尚未给激活、临时聚合、通信缓冲和框架留空间；“53B 装得下”不能直接解释成可成功训练 53B。采用不同精度配方时也应换账本。ZeRO-1/2 确实减少状态占用，但参数仍完整复制，参数容量不能随设备数无限增长；ZeRO-3 才进一步分片参数。

## 3. 为什么前两个 stage 的通信量可以接近 DDP

all-gather 让每人得到各片拼成的完整数据；reduce-scatter 先把各人的同位置数相加，再把结果分片交给所有者。FSDP 可在算某层前聚齐该层参数，反向后把该层梯度归约到所有者。是否立刻释放完整参数，决定下一次是否还要聚齐以及瞬时峰值。

DDP 的梯度 all-reduce 可以分解为 reduce-scatter 与 all-gather。ZeRO-1/2 让梯度先聚合到负责更新它的 rank，本地更新相应参数，再聚合更新后的参数。

在理想带宽主导模型中，它们可以与 DDP 有相近量级的字节数，但启动次数、分桶、释放时机和重叠效率并不完全相同。因此，节省状态存储并不意味着实际运行没有额外成本。

ZeRO-3 常在前向与反向分别按需 all-gather 参数，再 reduce-scatter 梯度；也可以通过保留参数等配置改变次数。具体通信量需要说明重分片策略。

### ZeRO/FSDP 的生命周期补全

ZeRO-1 中各 rank 仍算自己的完整模型，只让某 rank 负责一段参数的优化器更新；reduce-scatter 梯度后，本地更新，再 all-gather 更新后的参数。ZeRO-2 进一步在反向逐段产生梯度时及时聚合、释放，不必长期保留完整梯度。ZeRO-3 则还分片持久参数，按层前向聚合、释放，反向再聚合、计算并发送梯度。它不是 PP：各 rank 仍处理自己样本的完整层序列。

预取下一层和当前层计算重叠，是“额外通信接近被隐藏”的条件，不是通信真正消失。跨节点带宽、层粒度与计算大小不足时，仍会有明显等待。Batch 又是有限资源：无限扩大 DP 和全局 batch 并不会等价于更多有效优化步骤。

### collective 与通信账本

这里使用 **All-Reduce = Reduce-Scatter + All-Gather**。root reduce 最后只让根节点得到完整归约结果，和 all-reduce 语义不同。“2×参数量”“3×参数量”比较假设每次发送元素位宽一致，并忽略有限 rank 的 `(r−1)/r` 和延迟；换精度、分桶、层粒度后必须按字节重算，不能直接把参数个数当字节。

### FSDP 的时序图

在 FSDP 中，先聚合第 i 个单元的参数，才能计算该单元；计算时可以预取 i+1。计算与通信重叠需要按依赖安排流水，不是“所有层一次全部聚合”。复用同一权重的计算图还可能触发多次请求。不同封装粒度、是否在前向后重新分片会改变峰值内存和通信次数。注意，FSDP 各 rank 依然执行完整层序列，不能画成只有一个 rank 执行一层的 PP。

## 4. 重叠不是“发起异步”四个字

异步提交只说明调用方未等待，真正重叠还需要计算和通信可并行、数据依赖允许、设备资源够用。预取是提前取未来层参数；提前太多会让多层完整参数同时存在，可能用峰值显存换得较短等待。

若第 i 层正在计算，可以预取下一层参数；若某层梯度已经就绪，可以提前通信。成功隐藏通信要求有足够独立计算可覆盖传输，而且显存允许保留额外缓冲。

太早预取会增加峰值，太晚预取会等待。bucket 太小被启动开销主导，太大又要等很久才开始。一个平均带宽很高的系统，也可能因依赖关系把大量通信暴露在关键路径上。

## 5. 流水线的气泡怎样估计

p 是流水阶段数，m 是一次更新安排的 microbatch 数。若每份含 b 个样本，数据并行度为 d_dp，则简单等大设置下全局 batch 为 b×m×d_dp。增加 m、增加 b、增加全局 batch 是不同动作。气泡公式还假定阶段足够均衡，不能从时间图填满就推出训练语义正确。

把模型分成 p 个耗时相近的阶段，处理 m 个 microbatch。简单均衡流水模型中，有用工作与填充排空的关系可近似为：

$$
\mathrm{efficiency}\approx\frac{m}{m+p-1}.
$$

例如 p=4、m=4 时约为 4/7，m=16 时约为 16/19。这个教学模型忽略阶段不均衡、反向调度和通信；它说明 microbatch 多可以减少相对气泡，但不保证真实利用率达到该值。

1F1B 等调度用更早的反向释放激活；一些 zero-bubble 思路把传回激活梯度与计算权重梯度分开安排。要同时检查更新依赖与内存，而不只画一张很满的时间图。

### 流水线中的三个 batch 概念

`(p−1)/m` 是平衡阶段、简化时序下**气泡时间/有效计算时间**，对应利用率为 `m/(m+p−1)`，不是利用率等于 p/m。m 是 microbatch **个数**，b 是每个 microbatch 的样本数；全局 batch 还需乘 DP 副本数。增加 m 和增加 b 是不同操作。 比较 batch=8 与128时的大管线差距，说明更多微批有助于填满管线，不证明任意扩大总 batch 都不损失优化效率。

### 反向的两个梯度和 zero bubble

对 `y=xW`、上游梯度 `G=dL/dy`，输入梯度为 `GWᵀ`，权重梯度为 `xᵀG`。前者需要尽早传给前一 stage；后者可以在数据仍可用且更新尚未开始的窗口中延后，用于填空闲段。“whenever”因此有边界：不能晚于参数更新，也不能丢掉所需 x/G。虚拟 stage 调度可能减少空闲，却增加阶段边界通信。

## 6. TP、SP 与 CP 不要混淆

TP 切层内矩阵；sequence parallel 常沿位置切分特定逐位置激活；context parallel 分担长上下文注意力工作；EP 把专家交给不同设备。一个 rank 可以同时属于多种组，不同并行“度”可能共享同一设备轴，因此不能看到几个数字就全部相乘。

张量并行 TP 分矩阵，减少每卡矩阵计算与参数；但 Norm、dropout 等操作可能仍复制激活。Megatron 风格的 sequence parallel 常把这些逐位置操作沿序列切开，在需要完整数据的边界使用 all-gather/reduce-scatter。

Context parallel 则进一步把长序列的 Attention 工作分布到多卡，交换 K/V 或相应中间信息。两者都和序列维有关，却不是同一套通信安排。

Attention、MLP 和 MoE 各部分可能采用不同的并行组。专家并行 EP 不是把每个专家的矩阵切得越来越碎，而是把完整或较完整的专家分给设备，再路由 token；这往往能保持较好的矩阵尺寸，但引入 all-to-all。

### 专家分布与激活存储

Zero-bubble 调度把反向的输入梯度（下游阶段急需）与权重梯度（可稍后计算）分开，以后者填空闲时间。它还受峰值激活、阶段均衡、更新依赖等约束，“零气泡”名称不保证任意配置零等待。

以一种带 dropout 的标准 Transformer 账本为例，按层把激活写成约 `sbh·(34+5as/h)` bytes，其中 s 为序列长、b 为本地 batch、h 为隐藏宽度、a 为头数。TP 后仍可能剩下不能按 TP 切分的约 `10sbh` 项；SP 进一步切分逐位置操作，选择性重计算/高效 attention 再减少二次项。这些常数来自特定结构、精度与保存策略，**不是所有现代模型的显存下界**。完整重计算可以进一步减少保存量，但增加 FLOPs，不能把“34”当成普适常数。

EP 保持专家矩阵较完整，往往比继续把小专家做 TP 更有利；代价是复杂的 dispatch/combine、负载和低延迟通信。Attention 和 MoE 层还可能需要不同并行配置：attention 想用较高 TP，专家却可能因此被切得过碎，所以有把两部分并行组解耦的方案。EP 不总能像独立积木那样与 DP/TP 任意相乘。

### 激活内存公式的适用条件

峰值图叠加参数、优化器、激活、梯度和临时量，峰值不一定在前向结束。`sbh(34+5as/h)`、TP 后的 `sbh(10+24/t+5as/(ht))` 来自特定结构和保存策略，系数已经包含精度字节；不能再无条件乘一次 bytes/element。

SP 利用 norm/dropout 不依赖**其他 token**这一点沿序列分片；LayerNorm 本身仍会在一个 token 的 hidden 维归约，不是 hidden 维完全独立的逐元素操作。TP+SP+选择性重计算得到 `34sbh/t` 是这份账本的配置结果。还可以重计算 MLP，因此这不是所有算法的内存下界。

### 专家并行与设备组不能机械相乘

EP 可以复用 DP 域，也可以将 Attention 与 MoE 的并行划分解耦。传统结构中 EP 可以是 DP 的子组；更灵活结构对 Attention 用 `TP×CP×DP×PP`，对 MoE 用 `ETP×EP×EDP×PP` 描述同一设备集合。两套划分不能全部相乘。这个区别也见 [Megatron 官方 Parallel Folding 说明](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/moe.html#moe-parallel-folding)。因此 EP≤DP 是某类实现的约束，不是 MoE 数学定律；EP 也不必严格小于 DP。

## 7. 如何组合并行

组合配置需同时画参数的所有权和样本流向。先找每层/每组是否能装下，再安排高频通信走快链路，最后扩大数据并行。改变上下文长度、训练阶段或全局 batch 后，可行配置可能变化，不能只沿用最初的容量表。

先确保容量：选择分片状态、TP、PP 或它们的组合。再考虑吞吐：把高频、强同步通信尽量放在更快的互联域内，让更少、较大的点对点通信跨较慢边界。最后用 DP 扩展样本吞吐，直到 batch、网络或优化效率遇到限制。

这是一套判断流程，不是“TP 永远等于 8”的规定。现代互联域大小会变化；模型长上下文阶段也可能需要更大的 CP。MoE 的并行维度还可能复用同一批设备，不能不加说明地把所有并行度直接相乘。

**补充理解：** 组合并行像给同一张地图画不同分区：有人按订单分，有人按工序分，有人按车间分。地图必须一致，否则“每个分区都看起来合理”，整体却对不上数据流。

经验流程是先用较快互联里的 TP/EP 和必要的 PP、状态分片解决容量，再尽量用 DP 消化剩余设备；长上下文阶段可能提高 CP、降低 DP。较小 dense 模型可只用 FSDP；大型 dense/MoE 则组合多种策略。所讨论的 OLMo、DeepSeek、Yi、Llama、Gemma 和框架配置例子用于说明这些差异，不能把其中某个数字配置移植到不同硬件后直接认定最优。

还要计入故障、检查点和恢复：模型能在理论上分片并不意味着长时间大集群训练可靠。应按阶段重新核算 FLOPs、激活、通信和可重叠部分，并保留对最大 rank 耗时的测量。听不清的问句不据猜测补成技术结论。

### 总览表中的简写要还原

FSDP 的通信应按实际阶段记录：本章流程是参数 all-gather 与梯度 reduce-scatter。用 DP 线性增加全局 batch 也是常用配置方式，不能当成必须：固定全局 batch 时，可降低每 rank 本地 batch，直到太小而低效。

纵轴是**计算时间/通信时间**，超过 1 意味着有机会隐藏通信，不是已经测得 100% 利用率；还受依赖、资源争用与重叠调度限制。梯度累积能减少每样本梯度同步频率、增加可调度的微批，但在某些 FSDP 设置中每微批仍会聚合权重，不能保证消除所有通信等待。权重复用与 loop Transformer 会改变计算和通信安排，但系统上的可行性不能用来推断未公开模型的架构。

### 扩展实验的比较条件

强扩展实验应固定模型与训练工作量，再增加设备数；如果同时改变模型大小、PP、DP 与 batch，比较的是整套配方。所引固定 175B/530B 模型实验属于前一种问题。另一个使用 **64 张 A100 GPU** 的实例中，TP=8 较优与当时的八卡高速互联域有关，不能视为所有网络的最佳值。重计算在相同小 batch 下可能稍慢，但也可能让更大的 batch 成为可行配置，进而改善整体吞吐。

### 阶段变化和故障表

Llama3 主阶段 `8×1×16×128=16384`，长上下文阶段 `8×16×16×8=16384`：卡数相同，将 DP 换给 CP，序列长度增大后仍维持约相同 tokens/batch。这是“阶段改变要重新选择并行”的具体例子。148 是某故障类别的中断次数，不是148张不同GPU，也不是单卡故障概率；恢复、检查点和排障能力同样决定有效训练时间。Gemma2 摘录区分不同模型大小的 TP/DP 配置，不能把最大模型的768副本数套给全部规模。

### 训练实例、框架建议与未知项

Dolma 是数据集，OLMo 是模型，比较训练配方时要区分这两类对象。MoE 可以同时使用 EP 与 TP：EP 在设备之间分配专家，TP 切分单个算子的矩阵；以 EP 减少部分 TP 需求，并不意味着二者不能共存。

读并行配置时，先确认数值表示“未启用”“组大小为 1”还是“未知”。例如未启用 pipeline 应在设备乘法中按因子 1 计，不能真的乘以 0。其次确认各并行组是否独立：EP 可能复用其他维度的设备，不能直接把所有标签相乘，也不能用剩余商猜出 DP。最后区分框架推荐、第三方复现与原始训练配置，只有定义一致且来源明确时，设备总数的核算才有意义。

## 深入算例与补充理解

### 每卡参数量下降，临时峰值仍可能上升

假设一个 8 层模型按层进行 FSDP 聚合，每卡保存 1/P 的持久分片。计算某层时需要临时完整参数；如果还预取下一层，就同时持有两层完整参数。更激进的 overlap 可能减少等待，却让显存峰值增加。

因此容量规划应画时间轴：持久分片、当前完整层、预取层、激活、梯度 bucket 分别何时存在。只把“总模型字节/P”写进表格，是把动态资源问题误当静态存储问题。

### microbatch 数与 microbatch 大小要分开

有效 batch 固定时，把 microbatch 切得更小会增加 microbatch 数，有助于减少 PP 相对气泡，但每次矩阵乘法也变小，通信启动次数增多。若为了增加 microbatch 数直接增大全局 batch，又会改变优化问题。

一个好的 PP 调参实验应同时记录每个 microbatch 的大小、累积次数、DP 度和全局 token batch。只报告“microbatch=8”没有说明它是数量还是样本数，会导致完全不同的理解。

### PP、TP、DP 的设备数量算例

对一个没有复用并行维度的简单 dense 配置，TP=4、PP=2、DP=8，总共需要 64 张卡。每个 DP 副本由 8 张卡共同保存和执行一个模型；副本之间处理不同数据。

若加入 MoE 的 EP，可能把 EP 放在已有 DP 域中，也可能使用独立维度，具体依赖框架。此时不能未经检查就再乘一个 EP=8 得到 512。先画每个 rank 所属的通信组，再核对参数副本与样本流向。

### “更省显存”可能怎样提高速度

激活检查点增加 FLOPs，却可能让本地 microbatch 从 1 增到 4，形成更大的 matmul，并让通信更容易被覆盖。最终每 token 耗时有可能下降。这是内存优化通过改变可行工作点，间接改善速度。

反过来，过度分片把矩阵切得太小，也可能让每卡的理论 FLOPs 更少、实际耗时反而增加。比较方法时应看在相同质量与全局 batch 约束下的最佳可行配置，而不是只看同一个局部设置。

## 独立完成一个小算例

10 亿参数按 16 bytes 账本静态占 16GB。8 卡时，DDP 每卡仍为 16GB；ZeRO-1 为 4+12/8=5.5GB；ZeRO-2 为 2+14/8=3.75GB；ZeRO-3 持久分片为 16/8=2GB。最后一个数绝不是运行峰值：当前完整层、预取层和激活仍需另加。

## 8. 自测与容量练习

1. 按本章 16 字节账本，8 卡 ZeRO-2 每卡的静态字节/参数约多少？
2. 为什么增加梯度累积可以帮助重叠，却不能凭空改善参数 all-gather 的所有等待？
3. 阶段1耗时是其他阶段两倍，简单气泡公式会失效在哪里？
4. 给出一个 TP 加大后反而更慢的原因，并指出应测什么。

**参考思路：** 第一问是 2+14/8=3.75；还必须另加激活和瞬时完整层。小矩阵利用率下降、通信频繁、分桶与拓扑都可能让 TP 过大变慢。

### 逐题推理

1. 16 bytes 账本的 ZeRO-2 为 2+14/8=3.75 bytes/原模型参数/卡；仍需加激活、临时聚齐层与缓冲。
2. 累积提供更多可交错工作，但参数使用前仍必须可用；没有独立计算覆盖的 all-gather 依赖不会凭空消失。
3. 一个阶段慢两倍会形成瓶颈，其他阶段即使排得很满也要等待；均衡阶段的 m/(m+p−1) 不再是准确预测。
4. TP 太大可能使局部矩阵变小、同步更频繁或跨慢链路，应比较每 token 时间及暴露通信，而非只看每卡 FLOPs。
