# 11 L10｜推理系统：KV cache、量化、推测采样与动态批处理

> Spring 2026 · 中文教材初版。主要依据用户提供的 `lecture-10.txt`，并结合[官方 课堂代码](https://github.com/stanford-cs336/lectures/blob/de53a9f979a6ee35f7d13a5e1aadee5ea1afc58e/lecture_10.py)。 时间定位：约 00:00–45:01 推理模型与指标；50:02–70:00 压缩；约 70:00–85:23 推测采样与缓存管理。正文按知识逻辑重组，不是逐字翻译；“补充理解”与教学算例为作者解释。未逐句对照录音。

## 1. 先把“快”说清楚

TTFT 是从请求进入系统到首个 token 出现的时间，包含排队、调度与 prefill 等；每 token 延迟描述单个请求生成速度；总吞吐描述许多请求合计每秒产生多少 token。它们经常相互制约。

一个把 GPU 跑得很满的大 batch 系统，可能让早到的请求等待很久。在线服务通常需要在延迟约束下优化 goodput：按质量与延迟要求完成了多少有效工作，而不是仅追求最高平均 token/s。

## 2. Prefill 与 decode 的工作不同

Prefill 已经知道整个 prompt，可以并行计算所有位置的隐藏状态，形成较大的矩阵乘法。Decode 每次只知道接下来一个 token 的输入，不同生成步之间有依赖。

如果每一步重新计算全部历史，会重复许多工作。KV cache 在每层保存历史 Key 和 Value，新 token 只产生新的 K/V 和 Query，再读取已有缓存。此前位置的因果表示不受未来 token 影响，所以可以复用。

缓存通常不保存每一步的 Query：旧 Query 已经完成了它的输出计算，而未来位置需要读取的是旧 K/V。

## 3. KV cache 容量手算

对 L 层、B 个请求、每请求 S 个缓存 token、h\_kv 个 KV head、head dimension 为 d\_h、每元素 b 字节：

$$
M_{KV}=2LBS h_{kv}d_hb.
$$

前面的 2 表示 K 和 V。教学算例：L=32、B=1、S=4096、h\_kv=8、d\_h=128、BF16，得到 512 MiB。若 KV head 增为 32，则变成 2 GiB。不同精度、潜变量缓存或跨层共享需要重新计算。

请求生成越长，占用越大；并发请求越多，缓存总量也越大。因此降低 cache 不仅可以减少读取，还可能释放容量以接纳更多请求。

## 4. 为什么 batch 有帮助，但不能解决一切

MLP 权重被不同请求共享，batch 变大可以把一次加载的权重用于更多 token，提高算术强度。但每个请求的 KV cache 通常不同，Attention 部分的缓存读取不会自动被 batch 大小摊薄。

所以总吞吐可能先明显增加，随后受 cache 带宽、计算或容量限制。共享前缀是另一种复用，需要明确的缓存匹配与生命周期管理，不能把不同请求的任意 K/V 混用。

## 5. 两类有损节省

**架构改动：** GQA、MLA、局部 Attention、跨层共享等减少 cache 或运算。它们改变模型结构，需要训练、适配或蒸馏并检查效果。

**量化与裁剪：** 量化用低位表示近似原数值，配合缩放和必要的校准；裁剪移除部分层、头或维度，再用训练修复行为。稀疏参数减少不等于真实算子更快，必须有匹配的执行方式。

PTQ 是训练后量化，QAT 在训练中模拟量化误差。敏感通道、离群激活和分组缩放都会影响误差。不能只看“权重减少四倍”就宣称“服务快四倍”，因为解码还包含 KV 读取、解量化和调度。

## 6. 推测采样为何可以保留目标分布

小 draft 模型先提议几个 token，大 target 模型一次验证这些位置，利用“验证多个已知 token 比逐个生成更并行”的差异。

设 draft 分布为 q、target 为 p。提议 x 后，以 ​min(1,p(x)/q(x)) 接受；若拒绝，从归一化的 ​max(p−q,0) 残差分布采样。接受路径贡献 min(p,q)，拒绝后的修正补足剩余部分，因此最终仍为 p。

教学算例：p=\[0.6,0.4]、q=\[0.8,0.2]。提议 A 的接受概率 0.75，直接接受 A 的总概率为 0.8×0.75=0.6；提议 B 总被接受，概率为 0.2；拒绝 A 的 0.2 概率补给 B，最后 B=0.4。

这是分布正确性的结论，不是“输出与原随机种子逐字一致”。多 token 版本还要在首个拒绝处截断后续提议，正确处理对应前缀的条件分布与额外 token。

## 7. Continuous batching 与分页

请求不断到来，结束时间也不同。Continuous batching 每轮重新安排活跃请求，让新请求补入空位，避免等待整个旧 batch 完成。它还要处理 prefill 与 decode 的资源竞争，长 prompt 可能影响其他请求的延迟。

PagedAttention 把逻辑连续的 KV cache 放进物理上不连续的块，用 block table 找到它们。好处是减少预分配和碎片；共享前缀可复用块，分叉写入时使用类似 copy-on-write 的机制。

**补充理解：** 分页不减少模型“应该记住”的有效 token 数，而是更好地管理存放这些 token 的空间。它与 FlashAttention 主要减少中间结果 IO 的目标不同，可以组合。

## 8. 如何评估一次优化

固定模型、采样设置、输入和输出长度分布、到达模式及质量要求；报告 TTFT 与 token 延迟的分位数、吞吐和峰值显存。区分预热与稳态、命中前缀缓存与不命中、低负载与饱和负载。

## 深入算例与补充理解

### 用带宽下界检查一个 decode 声明

假设每步必须读取 20GB 权重，暂时忽略 KV 与其他开销，有效带宽为 2TB/s，则读取下界约 0.01 秒，即 10ms。若有人报告同样模型在相同假设下每步仅 1ms，应先检查权重是否常驻更快缓存、模型是否分片、精度是否不同，或计时是否漏了同步。

这个估计不是实际速度预测。它用来发现口径不一致，尤其要区分“单请求每秒 token 数”和“整个 batch 的总 token/s”。batch=100 时，每轮即使 10ms，也可能对应总吞吐 10000 token/s，而单请求仍约 100 token/s。

### 为什么 prefix cache 需要精确匹配

缓存取决于 token 序列、模型权重、位置表示和相关配置。看起来语义相同的两段话，并不自动拥有可交换的 K/V。哪怕只改了前面一个空格，使 tokenization 发生变化，后续表示也可能变化。

同一个 prompt 分叉生成多个回答时，可以共享尚未分叉的部分；分叉后的内容不同，需要独立继续。分页与引用计数有助于管理共享，copy-on-write 还需正确处理最后一个未写满块。

### 推测采样的速度收益由什么决定

draft 太大，提议成本高；draft 太弱，接受率低；一次提议太长，又可能在很早就拒绝，浪费后面计算。target 验证的并行程度与 KV 管理也影响收益。

因此合理的实验要同时记录 draft 时间、target 验证时间、每轮接受 token 数分布和总延迟。即使采样分布数学上正确，边界处理、温度转换、top-p 截断后的概率与缓存回滚仍可能写错。

### 从容量约束到调度约束

两个请求都能分别装进显存，并不意味同时执行就合适。长 prefill 可能占用大量计算，拖慢许多 decode 请求；频繁抢占则可能要重算或搬移 cache。分块 prefill、优先级与准入控制是在不同负载下平衡这些问题。

服务效果应在给定到达率下测量，观察队列是否稳定。若输入请求比系统长期处理能力更快，排队会不断增长，任何低负载延迟数字都不能代表饱和后的体验。
