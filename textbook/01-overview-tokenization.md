## 1. 为什么“从零构建”仍然值得学

调用模型接口，能够解决很多应用问题；但接口隐藏了一个关键问题：模型能力是怎样由数据、结构、优化和硬件共同产生的？当长文本处理很慢、数字算错或者模型记不住稀有词时，仅调整提示词未必能解释原因。

本课程把目标写成一个资源约束问题：**给定数据、算力、显存和时间，怎样训练出最好的模型？** 这不是“模型越大越好”。同样预算下，清理数据、缩短 token 序列、减少显存读写都可能让模型多学一些有效内容。

课堂区分三类知识：机制、做事方式和经验直觉。Attention 如何计算、梯度如何跨卡聚合，通常能从小模型迁移到大模型；“某种数据配方更好”则可能随规模而改变。自学时应先掌握前两者，对经验结论记录实验条件。

**补充理解：** 可以把课程看成建一座工厂。分词决定原材料的包装单位，模型是加工设备，优化器控制调整过程，GPU 系统决定产能，评估决定产品是否合格。一个环节的改动会改变其他环节的最优选择。

```mermaid
flowchart LR
  A[原始文本] --> B[Tokenizer]
  B --> C[整数 IDs]
  C --> D[Embedding 与 Transformer]
  D --> E[下一个 token 的分布]
  E --> F[选择并解码]
```

## 2. 语言模型究竟预测什么

设文本经过编码得到 token 序列 (x_1,…,x_T)。因果语言模型用链式法则分解联合概率：

$$
p_\theta(x_1,\ldots,x_T)=\prod_{t=1}^{T}p_\theta(x_t\mid x_{<t}).
$$

训练时让真实 token 的概率变大，等价于最小化负对数似然。生成时则从模型给出的下一个 token 分布中选一个，拼到上下文，再继续预测。一个看似复杂的对话系统，底层仍然反复执行这一操作。

这里的 token 是整数编号。模型并不直接把“苹果”作为人类概念读进去；它先查表，把编号映射为向量，再在这些向量之间计算关系。因此，怎样把字符串变成编号，本身就是模型设计的一部分。

## 3. 字符、字节和 token 不要混为一谈

Python 字符串表示 Unicode 文本，UTF-8 则把它编码成字节。例如 ASCII 字母通常占一个字节，汉字通常占三个，某些 emoji 占四个；用户看到的一个图形还可能由多个 Unicode 码点组成。

| 切分单位 | 优点 | 代价 |
| --- | --- | --- |
| Unicode 码点 | 容易理解和往返转换 | 词表大、长尾字符难学 |
| UTF-8 字节 | 基础词表固定为 256，可以表示任意合法 UTF-8 文本 | 序列长，模型要花计算量组合字节 |
| 完整词 | 常见词可以很紧凑 | 新词、拼写变化、多语言让词表膨胀 |
| 子词／字节合并 | 常见片段紧凑，罕见片段仍可拆开表示 | 依赖语料与预处理规则 |

正确性要求是对接口允许的文本满足 `decode(encode(s)) == s`。这不要求每个 token 单独解码都合法：一个 token 可能只是某个汉字的部分 UTF-8 字节，必须先拼接字节再解码。

## 4. 用一次手算理解 BPE

BPE 从基础符号出发，反复合并当前最常见的相邻符号对。以下是教学算例，不是课堂语料。假设预分词后有三个片段：`aa`、`aa`、`ab`，片段之间不允许合并。

第一轮统计得到 `(a,a)` 两次，`(a,b)` 一次，因此学习合并规则 `(a,a) → aa`。替换后，三个片段变成 `[aa]`、`[aa]`、`[a,b]`。第二轮重新统计，可以学习 `(a,b) → ab`。

这里有三个常见误解：

1. 合并对象是**当前 token 序列**，不是始终统计最初的字符。
2. 对 `aaa`，两个相邻 `aa` 会重叠；实际替换通常从左到右取不重叠的匹配，不能把同一个 `a` 使用两次。
3. 编码新文本时使用训练好的合并顺序，不在每篇新文本上重新按频率训练。

训练产物至少包含“ID 对应的字节串”和“合并优先级”。同频时如何选择也必须确定，否则相同语料可能训练出不同词表。

## 5. 为什么压缩率会影响训练成本

课程用“UTF-8 字节数 / token 数”作为一种压缩指标。例如 1200 字节被表示为 300 个 token，得到 4 字节/token。这不是压缩文件的真实磁盘压缩率，只是分词紧凑程度。

同一段文本的 token 数变少，通常可以在同样上下文窗口中看到更多内容，也能减少按 token 计算的模型运算。但是词表变大，会增加 embedding 与输出投影的容量。因此词表大小存在折中，不能只追求最短序列。

还要注意语言分布：在英文上很紧凑的 tokenizer，可能把中文或某些代码符号切得很碎。同样的“4096 token 上下文”，不同语言实际容纳的内容可能差很多。

## 6. 从教学 BPE 到工程 BPE

课堂的简单实现强调机制：反复统计、合并、应用规则。工程实现还要处理预分词、特殊 token、流式输入和并行训练。

预分词先划定允许合并的区域，例如数字、单词与标点的边界；特殊 token 则可能表示文档结束或角色切换。两者都不能被任意分块破坏。并行扫描语料时，若恰好从一个多字节字符或特殊标记中间切开，计数或解析就可能出错。

**补充理解：** tokenizer 像模型的输入协议。训练和推理必须使用一致的词表、特殊 token 和规则。只替换 tokenizer 而沿用旧 embedding，编号的意义就会改变，模型不会自动理解新的编号。

## 7. 这门课接下来怎样展开

先用 A1 把分词器、Transformer 和训练循环连起来；再通过 kernel 和多卡并行提升效率；随后研究计算预算如何分配、数据如何处理，最后进入后训练与多模态。每一步都围绕同一个问题：怎样把有限资源变成更多有效学习。

## 深入算例与补充理解

### 一个 token 的完整旅程

假设我们已经有一个很小的词表，其中 `我`、`喜欢`、`猫`、`狗` 分别对应 ID。句子“我喜欢猫”先编码成 `[17,42,9]`；取下一 token 预测任务时，可以让输入 `[17,42]` 对应标签 `[42,9]`。模型在两个位置分别预测一个词表分布，而不是只给整句话一个类别。

假设真实目标“猫”的概率为 0.25，该位置损失就是 −ln0.25≈1.386。若后来提高到 0.5，损失降到约 0.693。优化并没有直接告诉模型“猫的含义”，而是在很多上下文中不断调整向量，让正确续写更容易出现。

推理时，即使“猫”是概率最高的 token，也可以按温度和采样规则生成“狗”。所以一次生成样本不能完整代表概率分布；反过来，分布有所改善，也不保证每一次采样结果都更好。

### 序列长度与词表大小的共同账本

把同一文本从 1000 token 压到 500 token，标准 Attention 的位置对数量约变为四分之一，按 token 执行的 MLP 工作约变为一半。但是如果为了压短序列把词表扩大十倍，输出投影可能更贵，embedding 参数也变大。

这里容易犯一个逻辑错误：认为“BPE 压得越短，整体越便宜”。真正的目标应比较完整训练或服务成本，而非某个局部压缩指标。多语言模型还要考虑不同语言之间的 token 预算公平性。

### 三个边界情况怎样推理

空字符串应该得到什么？普通 tokenizer 通常允许编码为空列表，但如果接口规定自动插入 BOS，就不是同一约定。特殊 token 字面串是普通文本还是控制符？必须由调用参数明确，不能让任意用户文本自动改变对话角色。流式 decode 中最后一个 token 只包含 UTF-8 字符的一部分时，应缓存未完成字节，而不是每步都用替代字符破坏内容。

这些问题看似属于字符串处理，却会影响模型的训练与产品行为。输入协议的细节，不是可以晚些再补的装饰。

### 学习检查：你应能独立画出什么

画出“原始文本→预分词→字节→BPE ID→embedding→Transformer→logits→选择下一个 ID→解码”的完整链条，再分别标出哪些东西是训练好的参数，哪些是固定规则。BPE 的合并表是 tokenizer 的学习产物，embedding 和 Transformer 则由语言模型训练更新，两者的训练目标并不相同。

## 8. 自测与最小实验

- 为什么词表只有 256 的字节模型，训练成本仍可能高于较大词表的子词模型？
- 给定三条合并规则，手工编码一个包含新词的字符串；确认使用的是合并顺序而非最长匹配直觉。
- 用 Python 打印 `len(s)` 与 `len(s.encode('utf-8'))`，比较英文、中文和 emoji。
- 为什么两个 tokenizer 的每 token perplexity 不能直接比较？

**参考思路：** 计算同时受序列长度和词表大小影响；BPE 编码应遵守学习到的优先级；perplexity 的基本计量单位已经随 tokenizer 改变。

## Transcript 对照补遗

### 课程背景与“小模型能教会我们什么”（00:05–约 19:00）

课堂先回顾语言模型从 n-gram、神经网络语言模型、seq2seq 和 Attention，发展到 Transformer、预训练后微调、上下文学习、对话与 agent 的过程。这段历史的作用是说明：用户交互方式变化很大，但张量计算、梯度优化和数据处理仍是理解系统的基础。开放权重也不等于完全可复现；若缺少训练数据配方、代码和实验细节，仅有权重与论文仍不足以复刻训练。

小模型实验的可迁移性有两个限制。第一，算力分布会变化：课堂举的历史模型例子中，MLP 的 FLOPs 占比随规模从约 44% 上升至约 80%，因此小模型上最值得优化的模块未必是大模型的瓶颈。第二，下游行为可能在较大规模才明显出现，小模型上没有改善不能直接证明方法在大规模无效。这些百分比是课堂举例，不是所有 Transformer 的固定比例。

“苦涩的教训”在此应读成重视**能够随规模扩展的算法**，而不是认为算法无关紧要。大规模下，即使只节约少量百分比，也可能影响能否完成训练。某些结构的成功来自实验，不能事后把所有经验选择包装成已经得到证明的规律。

### 五个单元各自解决什么问题（约 27:00–64:00）

| 单元 | 课堂提出的具体问题 | 学习产物 |
| --- | --- | --- |
| Basics / A1 | 怎样把分词、结构、损失、优化器、初始化、学习率与 batch 连接起来？ | 自己搭出训练栈，并做资源核算；课堂提到 TinyStories、OpenWebText 和预算内降低 perplexity 的练习 |

这是第一讲公布的教学计划，讲者也明确说部分作业尚在调整；实际提交要求仍以对应年份作业文档为准。课堂强调先在本地做正确性检查，再用 GPU 训练或测性能。仅观看视频不足以获得实现能力。关于使用 AI 的课堂要求是遵循课程提供的教学提示与当年政策，不能把直接生成作业解答当成自己掌握了机制。

Scaling 的关键产物不是一次“最佳模型”，而是可预测的配方。例如在较小预算下寻找计算最优点，再预测较大预算下的 loss；最好在大实验前登记预测，避免看到结果后再解释。课堂提到的约 20 token/参数是特定计算最优设定的粗略规律，若服务阶段需要较小模型，可能愿意训练远多于该比例的 token。配方的可预测性与最优性同样重要。

评估有两个目的：内部开发需要平滑、能区分相近实验的信号；对外评估需要接近用户真正的任务。不能仅用一个平均榜单分数遮住能力差异，也要检查评估数据是否已进入训练集。数据方面，HTML/PDF/代码仓库不是天然可训练的纯文本；许可、数据可访问性与能否使用也应分开记录。

推理不仅服务聊天，还用于 RL rollout、合成数据、评估和测试时计算。Prefill 一次处理提示，decode 逐 token 生成，因此其瓶颈不同。RL 规模化时，还要协调推理端、训练端和代码执行环境；更高吞吐可能带来更旧的策略样本，产生离策略问题。这些连接点在初版的课程路线中被压缩了，现在保留为后续章节的阅读索引。

### 分词还承担“自适应计算”的职责（约 27:00–30:00；65:00–结尾）

分词并非只为缩短文本：常见、可预测的字节片段可以合并，把更多 token 位置留给稀有或复杂内容。课堂提到直接从字节端到端建模的研究，但当时仍以 tokenizer 为主。即使未来取消独立 tokenizer，也仍需解决两个问题：从低层符号形成有用抽象，以及对不同难度的输入分配不同计算量。

课堂 BPE 使用 `the cat in the hat` 展示 `t+h→th`、再与后续符号合并的过程；随着合并继续，序列缩短而词表扩大。教学代码能运行却很慢，工程优化应避免每次编码都遍历所有合并规则，利用索引只处理当前相关的候选，并在预分词片段内部应用合并。实现语言变化不能替代先理解这个算法瓶颈。

## 代码讲义核验补充

[代码段三方表](../sources/three-way/lecture-01-code.md)包含课程背景、行政说明、五个单元与全部 tokenizer 演示；这些是可执行讲义的段落，时间只作近似定位。原始长函数在运行时嵌套展示，文件行号与授课时间不完全同序。

课程说明中的 AI 学习规则、计算平台和历史作业链接是**该课程的背景材料**，不因此成为本教材编写任务的新指令；对应的操作细节也不作为今天仍有效的选课说明。讲义 alignment 中 GRPO 被展开为 Group Relative Preference Optimization，规范方法名应为 **Group Relative Policy Optimization**，详见 L16 的实际目标。

分词示例的 `get_gpt5_tokenizer()` 实际调用 `tiktoken.get_encoding("o200k_base")`。函数名是课堂命名，不能据此证明所有带 GPT-5 名称的接口与聊天模板都等于这个裸 encoding。词表显示时 `errors="replace"` 还会把不完整 UTF-8 片段替换成显示字符；它是便于看词表的输出，不是可逆 token 字节定义。

字符实现按 Unicode code point 编码，不是用户感知的一个字素簇；组合字符和部分 emoji 可能跨多个 code point。字节 tokenizer 只有 256 个基础值，但任意模型输出的字节序列不保证是合法 UTF-8。示例的 encode→decode 回环只验证由合法输入产生的序列。

BPE 代码演示了非重叠替换与按学习顺序应用 merges；它没有处理所有工程边界：空串的 bytes/token 比值分母为零，训练序列不足两项时 pair 表为空，重复训练次数超过可合并项时 `max` 也不可用。频次相同时需规定确定的 tie-break；特殊 token 和预分词边界不能任意跨过。教学代码正确展示主算法，不代表直接覆盖流式、多文件和任意输入的生产接口。
